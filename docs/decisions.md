# Decisions

The board's settled decisions. Every change has to respect them. If a task would break one, stop and ask the owner with a decision on the board ([Decisions](tasks.md#decisions)) instead of working around it. When the owner settles a new one, add it here, in the same pull request as the change it allows.

What breakaway is and isn't (free and self-hosted, an install keeps its data, the person who runs the board decides, one claim per task, Taskwarrior as a first-class way in) is in [`AGENTS.md`](../AGENTS.md#what-breakaway-is-and-isnt), and the claims breakaway makes about itself are in the [brand guide](../brand/README.md#claims-that-must-stay-true).

## Decision log

The board began inside samewave, the first install, so these entries were first made in samewave's decision log. They keep their dates, and they name samewave where it was that install.

Every item on samewave's old work list was imported under its work ID. Specs go in `docs/specs/`. (The owner's choices.) | [The manual](tasks.md), `CLD-22` |

Until the pipeline is built and the owner turns it on, deploys stay manual and with the owner. (The owner's decision.) | [CLD-27](specs/CLD-27-continuous-deployment.md), `CLD-28` |
| 29 Sep 2026 | **Deploys run through a pipeline the owner controls** (replacing "Deploys stay manual and with the owner"). After the required check passes, the Deploy workflow deploys, checks, and rolls back a failed check. The owner can pause it (`DEPLOYS_PAUSED`), and changes to production outside it stay the owner's. Because merging deploys, **the owner merges every pull request, Dependabot's included** (replacing an earlier rule where an agent merged them). (The owner's decisions, from the approved spec.) | [CLD-27](specs/CLD-27-continuous-deployment.md), `CLD-29` |
| 30 Sep 2026 | **The board can merge for the owner.** Two settings, **Keep branches up to date** (update every open pull request that falls behind `main`) and **Merge when green** (every open, non-draft pull request merges once its required checks pass, Dependabot's included, so it deploys). They're off by default, live only in the owner's browser, act only while the board is open there, and use the same cookie-only endpoints as the buttons, so no agent can turn them on or use them. Turning one on is the owner's intent to merge, so "the owner merges every pull request" still holds. (The owner's decision, `CLD-98`.) | [Pull request settings](tasks.md#pull-request-settings) |
| 30 Sep 2026 | **Production changes when the owner promotes a staging build**, not when a pull request merges (replacing "merging deploys production" and "the pause variable and Roll back are the brakes", 29 Sep 2026). A merge deploys staging only. The owner presses **Promote to production** on the board (or runs the Promote workflow), which ships the latest successful staging build, built once from the tested commit, with every pending migration in order. Tags and GitHub releases are for production only; staging builds are pre-releases. Roll back stays production only and is never paused. `DEPLOYS_PAUSED` pauses production (Promote) and the board's Worker, not staging. Hotfixes take the same path. The owner still merges every pull request. (The owner's decisions.) | [IDEA-10](specs/IDEA-10-promote-releases.md), `IDEA-10` |
| 2 Oct 2026 | **One board runs several repositories** (the owner's decisions in `CLD-119`, 1 Oct 2026). Every task belongs to one repository (no `repo` means the default repository, samewave on that install). A work-ID prefix belongs to one repository, while Ideas (`IDEA`) and Routines (`RUN`) are shared by the whole board. Dependencies may cross repositories, but a pull request closes only its own repository's tasks. Each repository has its own Claude routine, under shared agent limits with an optional cap per repository, and its own agent prompt in its checkout, reviewed like code, that includes the board's shared core; the routine on claude.ai holds only a stub that points to it. A saved routine belongs to one repository. A broken connection shows on Connections and as an inbox note, without a push. Each repository's `AGENTS.md` says how to build there; the board's skill and the prompt's core say only how to use the board. | [IDEA-14](specs/IDEA-14-multi-repo.md), [Repositories](tasks.md#repositories) |
| 4 Oct 2026 | **Features and chase** (the owner's answers on `BRK-82`). A feature is its own record that tasks join by carrying its slug as a tag, **one feature per task**. **The release is the feature's**, not the task's: release tags on tasks stay readable only as a fallback, and new tasks don't get them. A chase starts agents only on the owner's say-so, through each repository's own routine and under the board's shared limits; it never merges, deploys, or answers a decision, and stops at what only the owner can do. **Inside a chase, one agent per area becomes a per-chase number** (`parallel`, default 3; never two agents on related tasks), and outside a chase it stays one. **A chase starts after** security fixes, general agents, and other tasks that start by themselves. | [IDEA-28](specs/IDEA-28-features-and-chase.md), [Features](tasks.md#features), [Chase](tasks.md#chase) |
| 4 Oct 2026 | **Kickoff** (the owner's answers on `BRK-130`, all as recommended). **A routine can be connected from a form on the board**, which keeps its URL and token itself, encrypted at rest with a key derived from the sync key, never shows them again, and never returns them from any API: the one exception to "the Worker reads secrets and never writes one" (IDEA-14), for routine URLs and tokens only, while every Secrets Store secret is still written only by the owner, and `agents-connect` keeps working and wins when both exist. **The board writes an empty repository's first commit** through its GitHub App, with the files `repos init` adds, on the owner's press; a repository with commits still gets `repos init` and a pull request. **A kickoff's decision has Send answers and carry on**, which sends the answers and starts the next kickoff run in one owner-signed press; Send answers alone stays beside it. **Pick for me means a Cloudflare Worker with static assets** for anything that runs in a browser, on the account the board already runs on; the agent recommends a stack only for what can't run there. | [IDEA-26](specs/IDEA-26-kickoff.md), [the manual](tasks.md#kicking-off-a-project), `BRK-132`, `BRK-133`, `BRK-134`, `WEB-35`, `WEB-38` |
| 5 Oct 2026 | **Planning on the peloton** (the owner's answers while shaping `IDEA-36`). **Every agent riding an open chase may change the chase's unclaimed tasks** in its own repository (description, done when, area, horizon, tags, and dependencies), add tasks to it, and delete the ones agents added after the chase started; for any other task it proposes deleting in a ping. **Tasks agents add to a chase join it, and the chase starts agents on them within its limits, also when nobody's watching.** A road captain, once started, runs the chase's peloton: it keeps the plan, and calls and closes huddles. **Agents stay listening only in chases, and huddles happen only on a chase's peloton**; a repository's peloton gets asks and mentions. **The owner posts on the peloton**, from the board only, and their posts are guidance like their messages. Installs are recommended to run on Workers Paid. | [IDEA-36](specs/IDEA-36-peloton-planning.md) |
